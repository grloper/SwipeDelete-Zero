## Required corrections

### M0-R1 — P1: The account guard does not survive a worker restart
**`PhotosUploadWorker.doWork/processRow`, existing `CloudUploadEntity` and disconnect behavior.** `boundAccountName` is initialized from whichever account is signed in at the beginning of each `doWork`. The persistent queue rows do not identify the account that authorized them. Code-path counterexample: queue an unstarted upload under A; stop the process or defer work; sign in as B; a new worker binds itself to B and drains the old queue. The per-loop comparison accepts B. The current implementation also checks identity only between rows, not throughout a large row's upload. `DriveCloudBackup.signOut()` itself only signs out the client/updates state.

Do not describe this as durable account-rotation protection. Persist the initiating account/consent binding for pending work and enforce it on resume, before subsequent network operations, and before writing success. Quarantine legacy/unknown-owner work; never silently reassign it. Cancel/pause outstanding work on disconnect with defined handling of already in-flight requests. If the needed persistence belongs to M1, explicitly block the affected cloud-upload paths for M0 and report that narrower capability instead of claiming this fixed. No account passwords or tokens belong in the manifest or logs.

**Acceptance:** production worker/orchestrator tests cover A -> restart -> B, sign-out during a row, and new work under B with old A work present. No old work begins sending data under B and no new chunk/commit/ledger-success operation is issued after an observed disconnect. Document the unavoidable boundary for a request already in flight.

### M0-R2 — P2: A second read 401 still refreshes the append credential
**`PhotosUploadWorker.processRow` read retry and outer `doWork` 401 catch.** The retried `uploader.getMediaItem(rToken, ...)` can throw a second `HttpStatusException(401)`. That escapes into the outer handler, which clears/refreshes the append token. Subsequent iterations repeat the read attempt and consume append retries for a read-permission failure.

Use phase/scope-specific typed auth outcomes or a tested scoped-auth helper shared by production code. After the bounded read retry is exhausted, return a read-auth/re-consent outcome; never forward that error into append-token refresh. Bound the initial token-acquisition/re-consent path appropriately as well. Propagate coroutine cancellation rather than translating it into ordinary failed-upload accounting.

**Acceptance:** actual orchestrator tests assert which token was invalidated, which scope/account was requested, exact request/retry counts, and final queue state for append 401, read 401 then success, read 401 twice, revoked consent and cancellation.

### M0-R3 — P2: Non-final session states are implicitly treated as active
**`PhotosUploader.querySession`, `PhotosUploadWorker.processRow`.** The code treats every status other than `final` as resumable, including missing/unknown/terminated states; invalid or missing received-size values silently become zero, and negative offsets are not rejected. Google's guide says a present status other than `active` indicates a terminated upload. The guide does not establish that every `final` query supplies a recoverable token body.

Implement explicit, validated session outcomes. Only resume a documented active state with a valid in-range offset. Handle lost completion receipts and terminated/expired/unknown sessions deliberately; never claim original verification from a byte count or arbitrary response text. Preserve bounded restart/backoff behavior. Keep one production session-response model, not an unconnected duplicate used only by tests.

**Acceptance:** HTTP fixtures exercise the REAL response parser and orchestration for active, finalized with/without a valid completion receipt, terminated/unknown/missing status, missing/malformed/negative/out-of-range offsets, expiry and cancellation. No fabricated tokens, no resuming a known terminated session, no unbounded restart loop.

Primary source checked: https://developers.google.com/photos/library/guides/resumable-uploads

### M0-R6 — P2: Empty query visibility is still promoted to confirmed deletion
**`MediaStoreRepository.inspectMediaState`, `PurgeEngine.confirmMediaPurged`.** Null cursors and exceptions now return UNKNOWN, which is an improvement. However, `!moveToFirst()` unconditionally means ABSENT without considering partial/revoked access or visibility uncertainty. Under Android's selected-media access model, an app's visible query result is not necessarily the device's complete library. The new tests stub the resulting enum rather than exercising this query boundary.

Add current access/visibility context and fail closed when absence cannot be distinguished from loss of access. Test permission denial, limited access/reselection, null/empty cursor, query exceptions and actual trashed state through the production resolver boundary. Keep pending rows and do not award reclaimed bytes for ambiguous results. This is a source-level finding; I have not reproduced the permission transition on a physical phone.

Primary source checked: https://developer.android.com/about/versions/14/changes/partial-photo-video-access

### M0-R7 — P2: Missing rows can indefinitely starve the rest of a capped batch
**`PurgeEngine.preparePurge`, `StagingViewModel`.** `staged.take(100)` happens before live-state resolution. With 150 rows where the first 100 are absent and the final 50 exist, the engine returns an empty result; the view model removes none of those stale rows. Retrying selects the same first 100 forever. The current cap test actually models the all-missing prefix but never asserts progress.

Separate bounded execution from queue reconciliation. Return explicit pending/blocked/already-missing/deferred results, do not count externally missing files as space reclaimed by the app, and allow later eligible items to be explicitly selected without silently dropping blocked ones. Keep the user informed about a partial batch. Test a real cancellation callback and ensure it launches no next batch and changes no remaining-item bookkeeping. Do not enable Play/cloud deletion to test this; use an isolated executor or the correctly scoped offline test path.
